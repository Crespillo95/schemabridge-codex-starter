# Judge-readable examples

`examples/final/` is generated by the implemented synthetic workflow. Do not hand-edit these files.

```bash
# Strict: refuses a missing commit or dirty tree.
make submission-package

# Development only: preserves an explicit non-release label.
make submission-package-dev
```

The strict command resets the scoped synthetic PostgreSQL volume, runs deterministic evaluation,
and records the clean source revision plus checksums. The current package was generated in
development mode because the combined M16–M18 tree is uncommitted; its
[manifest](final/manifest.json) therefore has `release_ready: false`.

The write-back generator is deliberately non-mutating: it runs the same approval/audit contract
through a labeled fake. Live DataHub publication/read-back is a separate integration test requiring
the scoped writer credential outside Git. Recipe reuse never executes the checked-in SQL; it
replans, recompiles, guards, and requests approval again.

The regenerated package uses the M21 `synthetic_enterprise` registry for its north-star artifacts
and reports five exact query cases. It intentionally remains `release_ready: false` while the
working tree is uncommitted. The root-level recipe and evaluation report are current M21 evidence;
older standalone SQL/validation files are retained for history. Judges should start with
`examples/final/` and confirm the manifest label before treating any artifact as release evidence.

## M23 control-plane examples

The current package is governed query evidence, not a control-plane backup or a substitute for an
operator run. No archive, signed manifest, DSN, raw workspace/actor value, OIDC envelope, HMAC or
identity key, token, environment dump, or unredacted CLI output belongs under `examples/`.

Operate M23 from a trusted operator job using the exact commands below. The runtime, reconciler,
migrator, and fresh restore DSNs are separate secret-manager inputs; the restore DSN is deliberately
not a command-line option. `DATABASE_URL` remains a read-only source credential and must identify a
different database. Start and migrate the dedicated local synthetic control service with:

```bash
make control-plane-up
make control-plane-migrate
make control-plane-check
```

`make control-plane-reset` is destructive only to that local synthetic control volume. It is not a
production rollout, rollback, or restore command.

The operator flow is review-first and fingerprint-bound:

| Operation | Review or preparation | State-changing command |
|---|---|---|
| Current authority | `.venv/bin/schemabridge control-plane status` | None |
| Immutable registry version | `.venv/bin/schemabridge control-plane registry prepare-version` | `.venv/bin/schemabridge control-plane registry publish-version` |
| Registry activation | `.venv/bin/schemabridge control-plane registry prepare-activation` | `.venv/bin/schemabridge control-plane registry activate` |
| DataHub pointer projection | `.venv/bin/schemabridge control-plane reconcile inspect` | `.venv/bin/schemabridge control-plane reconcile repair` |
| Registry rollback | `.venv/bin/schemabridge control-plane registry prepare-rollback` | `.venv/bin/schemabridge control-plane registry rollback` |
| Offline SQLite import | `.venv/bin/schemabridge control-plane legacy-import inspect` | `.venv/bin/schemabridge control-plane legacy-import apply` |
| Identity initialization | `.venv/bin/schemabridge control-plane identity inspect-evidence` | `.venv/bin/schemabridge control-plane identity initialize` once |
| Identity rotation | `.venv/bin/schemabridge control-plane identity prepare` | `.venv/bin/schemabridge control-plane identity approve`, then `.venv/bin/schemabridge control-plane identity complete` |
| Stale recipe | `.venv/bin/schemabridge control-plane recipe-migration prepare` | `.venv/bin/schemabridge control-plane recipe-migration publish` |
| Disaster recovery | `.venv/bin/schemabridge control-plane backup` creates artifacts | `.venv/bin/schemabridge control-plane restore` into a distinct empty target |

Use the complete flag sets and exact confirmation values shown in the
[root M23 operator path](../README.md#m23-durable-control-plane-operator-path). In particular:

- registry activation uses the fresh `proposal_fingerprint`; rollback creates a higher generation
  and never edits history;
- reconciliation repair uses both the exact `report_fingerprint` and `inspected_at`; unsafe
  ahead/conflict/corrupt/audit-gap findings stop;
- legacy `inspect` reserves metadata only and imports no target row; `apply` reinspects the
  unchanged offline file and quarantines ambiguity instead of inventing ownership;
- identity operations accept one owner-only, short-lived signed envelope and never emit raw claims
  or rewrite historical payloads;
- recipe preparation emits no SQL or preview rows; publication creates a new SQL-free version
  after an already completed, guarded, read-only workflow;
- backup writes owner-only archive/manifest files; restore rejects the source database, a non-empty
  target, altered artifacts, or any post-restore state/audit mismatch.

The prepare/inspect/status stages do not authorize their paired mutation. A human must review the
fresh exact output and supply its fingerprint, timestamp where required, and closed confirmation
phrase. Managed operator identity comes from trusted configuration; `--actor` cannot select a
different actor.

If sanitized M23 evidence is later generated, it may retain only inert facts such as migration
version/checksum, pseudonymous transition/approval IDs, activation generation, registry/pointer
fingerprints, projection status, state digest, bounded table/audit/quarantine counts, and explicit
command/result provenance. Review even `--json` output before committing it. These operations
write only the control plane or explicitly approved DataHub targets; none writes a source database.
